# Star Empires — Simulation Time & Determinism Contract

Этот документ фиксирует контракт игрового времени после Этапа 1 roadmap. Новые simulation-системы должны сохранять эти свойства, пока архитектурное решение не будет явно пересмотрено.

## Fixed-step модель

- Базовый simulation tick демонстрационной игры: **0.1 игровой секунды**.
- `SpaceSimGame` передаёт render delta только в `SimulationLoop`.
- `SimulationClock` переводит входные секунды в целые наносекунды и хранит accumulator в `long`.
- Экономические системы получают только одинаковый fixed delta каждого исполненного tick.
- UI, Scene2D и частота обновления диагностических панелей используют render time и не влияют на экономический результат.
- Пауза не накапливает пропущенное реальное время.
- `timeScale` изменяет скорость накопления игрового времени, но не размер simulation tick.
- Ограничение `maxStepsPerFrame` не отбрасывает backlog: неисполненные ticks остаются в accumulator и исполняются последующими кадрами.

## Порядок одного simulation tick

`SimulationLoop` задаёт внешний pipeline:

1. `GlobalEventManager.update(fixedStep)`;
2. `Engine.update(fixedStep)`.

В демонстрационном Ashley Engine системы зарегистрированы в следующем порядке:

1. `MarketSystem`;
2. `ConsumptionSystem`;
3. `ProductionSystem`;
4. `AsteroidSpawnSystem`;
5. `MiningSystem`;
6. `TradeAISystem`;
7. `PriceRecorderSystem`.

Изменение порядка является изменением модели и должно сопровождаться обновлением regression-тестов и объяснением причины.

## RNG

Одна игровая сессия имеет корневой seed `SimulationRandom`.

Подсистемы получают отдельные именованные RNG-потоки. В текущем demo используются как минимум:

- `economy-events`;
- `asteroid-spawn`.

Добавление нового случайного вызова в одну подсистему не должно сдвигать последовательность другой подсистемы. Новая подсистема со случайностью обязана получить собственное устойчивое имя потока.

## Игровое время событий и новостей

- `GlobalEventManager` хранит simulation time, а не wall-clock time.
- `NewsArticle.timestamp` — миллисекунды игрового времени от начала симуляции; это **не Unix epoch**.
- `System.currentTimeMillis()` не должен использоваться для причинно-следственных simulation-событий.
- Для сравнения границ экспоненциального scheduler используется локальный epsilon **1e-9 секунды** только как защита от арифметики `double`.

## Детерминизм и tolerance

Для одинаковых:

- initial state;
- root seed;
- набора зарегистрированных систем и их порядка;
- количества исполненных fixed ticks;

экономический core должен давать одинаковый результат независимо от render frame pattern.

`EconomicSimulationDeterminismTest` сейчас требует **точного совпадения**, включая:

- число ticks;
- event revision и активные события;
- позиции сущностей через `Float.floatToIntBits`;
- содержимое складов;
- рассчитанные рыночные цены через `Float.floatToIntBits`;
- состояние торгового FSM, баланс и выбранный маршрут;
- точки, начальные и оставшиеся запасы астероидов.

Отдельно допускается tolerance **1e-9 секунды** между `SimulationClock` и внутренним временем `GlobalEventManager`, потому что менеджер событий поддерживает суб-tick моменты экспоненциального расписания в `double`.

Если будущая система потребует ослабить точное сравнение экономического состояния, это должно быть отдельным архитектурным решением с численно обоснованным tolerance и regression-тестом. Нельзя просто увеличивать epsilon ради прохождения теста.

## Инварианты для будущих этапов

- Simulation-код не читает FPS для определения экономического результата.
- Simulation-код не использует системное время компьютера как игровое время.
- Случайность должна быть инъецируемой и воспроизводимой.
- Large render delta не должен молча уничтожать игровое время.
- UI-интерполяция может быть недетерминированной визуально, но не должна изменять authoritative simulation state.
