# План изменения процесса разработки

Статус: **ПРИНЯТ**, 2026-10-17. Постоянные правила вынесены в `AGENTS.md`
(раздел «Development process»); этот документ описывает переход и критерии готовности.

## Зачем

Оценка на 2026-10-17:

| Проблема | Факт |
|---|---|
| Приёмка «обычного пути» через реальные перелёты по сгенерированной галактике | сегменты по 2 млн тиков, checkpoint ~225 МБ, 99 файлов `.s25` (17 ГБ); частый итог — PARTIAL |
| Формат сохранений меняется почти в каждом срезе | native ≈v8 → v29 за 1–17 октября; каждый шаг — codec, миграция, legacy-тесты |
| Документация как журнал доказательств | 333 md / ~80 тыс. строк; по 23B 3129 + 1043 + 983 строки |
| Редкие коммиты | 8–17 октября без коммитов, затем один коммит на 109 файлов и 116 файлов вне git |
| Находки баланса оформляются как «следующий шаг доказательства» | шахтёр не может долететь до топлива с 10% резервом |
| Имена по истории, а не по предметной области | 388 классов `StageNN*`, `Stage228CampaignAuthority` — 3747 строк |
| Нет ранней проверки, что играть интересно | ручная приёмка отложена до конца Stage 23 |

Сильные стороны сохраняются без изменений: инварианты сохранения денег и массы,
детерминированный round-trip, полный gate `mvn -Ptest-parallel verify`, независимое ревью.

## Этапы

### 1. Правила работы — сразу
- [x] Обновить `AGENTS.md`: коммиты, сценарные тесты, политика сохранений, документация, баланс.
- [x] Записать в `docs/ui/stage23b_remaining_work.md` ссылку на этот план одной строкой.

Готово, когда правила в `AGENTS.md` закоммичены.

### 2. Сценарные тесты на построенном мире — главный приоритет
Цель: обычный игровой путь проходит через те же команды игрока и такты, что и в игре,
но на маленьком специально построенном мире и за секунды.

1. **Исследование (Codex researcher).** Как получить минимальный валидный мир:
   `PlayableTestWorldFactory`, маленький профиль генератора или авторский мир.
   Что из generated campaign (operators, markets, dispatchers, ownership) обязательно
   для команд игрока. Результат — короткая записка с путями к классам.
2. **`ScenarioWorld` в `src/test`.** Builder: 1–2 системы, короткие дистанции, станции
   с известным запасом/ценами/топливом, стартовый корабль игрока. Мир строится только
   публичными конструкторами домена; деньги/груз не «выдаются» в обход инвариантов.
3. **Первый сценарий — цикл шахтёра.** Покупка корабля → добыча → возврат → продажа →
   платная дозаправка → покупка станции. Через команды игрока, с сохранением и загрузкой
   в середине. Проверки инвариантов денег и массы такие же, как в текущих тестах.
4. **Тег `@Tag("scenario")`.** Сценарии входят в обычный `verify`; бюджет одного сценария — до 60 с.
5. **Длинные QA-путешествия** (`tools/qa/*Journey*`) переходят в режим soak: запуск
   по запросу или раз в неделю, не для приёмки отдельного среза.
6. **Очистка `target/`.** Старые `.s25` (17 ГБ) удаляются только после подтверждения
   пользователя; на них ссылаются evidence-записи в документах.

Готово, когда цикл шахтёра проходит сценарным тестом и следующий срез 23B
принимается сценарием, а не перелётом по галактике.

### 3. Заморозка совместимости сохранений до RC
- Поддерживаемые версии сохранений начинаются с первого RC (23G). Промежуточные
  dev-форматы не поддерживаются.
- Пока RC нет: один текущий native-формат. Версия поднимается только при реальном
  изменении структуры. Старое dev-сохранение отклоняется до любой mutation
  с понятной ошибкой — новых миграций не пишем.
- Существующие миграции и legacy-тесты не удаляются в этом этапе: решение об их
  удалении — отдельное, с ревью и подтверждением пользователя.
- Обновить `docs/persistence_model.md` и `docs/release/stage23b_player_checkpoint_change_control.md`
  короткой записью о политике.

Готово, когда политика записана и следующий срез меняет формат без новой миграции.

### 4. Компактная документация
- Создать `docs/status/stage23b_status.md`, не длиннее 150 строк: таблица
  «блок → готово / не готово / что мешает / как проверено».
- Новые доказательства (логи, тики, массы) остаются в `target/` или CI-артефактах;
  в документ — одна строка со ссылкой и итогом PASS/FAIL.
- Большие документы 23B не переписываются: они переносятся в `docs/archive/`
  как история, когда статус-таблица их полностью заменит.

Готово, когда статус 23B читается из одной таблицы.

### 5. Баланс — как дизайн
- Если обычный путь упирается в баланс (топливо, дальность, цены), это issue
  с меткой `balance`, а не «следующий шаг доказательства».
- Первая задача: шахтёр с 10% резервом не достигает ни одного дока с топливом.
  Решение (запас топлива, резерв, размещение заправок) — за пользователем.

### 6. Коммиты и CI
- Коммит после каждого зелёного среза (целевые тесты прошли). Пуш — с разрешения
  пользователя; CI (`.github/workflows/ci.yml`) запускает полный verify на каждый push.
- Не держать незакоммиченную работу дольше рабочего дня.
- Полный `verify` локально — перед пушем крупного среза, а не после каждого изменения.

### 7. Имена и крупные классы — постепенно
- Новые классы получают имена по предметной области, без `StageNN`.
- Существующие `StageNN*` переименовываются, только когда класс и так существенно меняется.
- `Stage228CampaignAuthority` и `WorldSimulation` делятся по ответственности,
  когда в них идёт новая работа. Перед первым делением — оценка Codex researcher.
- Отдельного большого рефакторинга нет.

### 8. Ранние плейтесты
- После закрытия каждого блока 23B — короткий ручной плейтест основного цикла
  (15–30 минут). Вопросы: понятно ли, что делать; интересно ли; где застрял.
- Находки — issues с меткой `playtest`. Полная ручная приёмка в конце Stage 23 остаётся.

## Как оценить, что стало лучше

Через две недели сравнить с базой на 2026-10-17:
- время от начала среза до зелёного коммита;
- доля срезов, принятых сценарием, а не перелётом;
- число bump-ов native-формата;
- объём новых строк документации на срез;
- число дней с незакоммиченной работой.
