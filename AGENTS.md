## Development process

Adopted 2026-10-17. Transition plan and rationale: `docs/development_process_plan.md`.

Acceptance and tests:
- A slice is accepted by targeted tests plus scenario tests (`@Tag("scenario")`) that drive
  the ordinary player path (player commands + world ticks + save/load) on a small authored
  world. Keep the existing money/mass conservation and exact round-trip checks.
- Long QA journeys over the generated galaxy (`tools/qa/*Journey*`) are soak runs: on request
  or weekly, never the acceptance gate of a single slice. Do not start one without the user.
- Run targeted tests while working; run full `mvn -Ptest-parallel verify` before pushing a
  large slice, not after every change.

Commits:
- Commit after every green slice (targeted tests pass). Never leave work uncommitted for
  more than a working day. Push only with user approval; CI runs full verify on push.
- New source files belong in the same commit as the code that uses them.

Save compatibility (until the first RC):
- Supported save versions start at the first RC (Stage 23G). Dev formats are not supported.
- Keep one current native format; bump it only on a real structural change. An older dev save
  is rejected before any mutation with a clear error. Do not write new migrations.
- Do not delete existing migrations or legacy tests without user approval.

Documentation:
- Stage status lives in a short table (`docs/status/`), at most 150 lines per stage.
- Evidence (logs, tick numbers, masses) stays in `target/` or CI artifacts; documents get one
  line with the link and PASS/FAIL. Do not append long evidence narratives to docs.

Balance and design findings:
- If an ordinary path is blocked by balance (fuel, range, prices, capacity), report it to the
  user as a balance issue and propose a design fix. Do not continue it as proof work.

Code structure:
- New classes get domain names, without `StageNN` prefixes.
- Rename an existing `StageNN*` class or split a large class (`Stage228CampaignAuthority`,
  `WorldSimulation`) only when it is already being substantially changed; get a Codex
  researcher assessment before the first split. No standalone big refactorings.

Playtests:
- After each Stage 23B block closes, propose a short manual playtest of the core loop to the
  user; record findings as `playtest` issues.

## Agent delegation

The main agent owns implementation and integration.

Use researcher when:
- A task affects multiple subsystems.
- Architecture or dependencies are unclear.
- Significant refactoring is proposed.

Use reviewer when:
- Implementation is completed.
- Public interfaces are modified.
- Simulation or persistence behavior changes.

Do not spawn subagents for trivial tasks.

Limit concurrency to two subagents.
Only the main agent coordinates integration.

Never merge into main without user approval.

## Claude Code: delegation to Codex

researcher and reviewer are Codex agents (.codex/agents/*.toml).
In Claude Code, call them through Codex CLI, not through Claude subagents:

- Research: `codex exec -s read-only -c 'windows.sandbox="unelevated"' "<researcher instructions from .codex/agents/researcher.toml>\n\nTask: ..."`
- Review of a branch: `codex review -c 'windows.sandbox="unelevated"' --base main "<reviewer instructions>"`
- Review of uncommitted work: `codex review -c 'windows.sandbox="unelevated"' --uncommitted "<reviewer instructions>"`

The `windows.sandbox="unelevated"` override is required when Codex is launched from
Claude Code: the user's default `elevated` sandbox fails there with
`helper_unknown_error: setup refresh had errors`, and Codex cannot run any command.

When to use Codex:
- Review: always use Codex for the reviewer cases above; keep `model_reasoning_effort="high"`.
- Research: only for cross-subsystem architecture questions or risk assessment of a large
  refactoring. Simple lookups (where a class is defined, who uses it) Claude does itself.
- For short Codex queries pass `-c model_reasoning_effort="low"`; the user default is `xhigh`.
- Images (sprites, textures, backgrounds, icons): generated by Codex, see below.
- Audio: Codex has no audio generation; Claude handles audio unless the user says otherwise.

Image generation (the only case where Codex may write files):
- Run `codex exec -s workspace-write -c 'windows.sandbox="unelevated"' "..."`.
- The prompt names the exact output path(s) under `src/main/resources/assets/` (or
  `target/` for drafts), the size, format and style reference (existing assets in the
  same folder), and forbids changing any other file.
- After the run Claude checks `git status`: anything changed outside the named paths is
  reverted. Claude views the image itself before accepting it.
- Wiring assets into code (sprite catalogs, renderers in `presentation/asset`) stays with Claude.

Rules:
- Codex runs read-only only; Claude owns all edits, commits and pushes.
- Run Codex in the background (runs can take minutes); at most two at once.
- Codex output is advice, not truth: verify findings in the code before acting.
- Report to the user which findings were accepted and which were rejected, and why.
